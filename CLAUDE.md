# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A **TREK plugin** (self-hosted travel planner, github.com/mauriceboe/TREK) called "trip-importer". It reconstructs a past trip from any combination of: Polarsteps ZIP/trip.json exports, booking confirmation PDFs/emails, photos with GPS EXIF, expense CSVs, and Google Maps Timeline JSON. Manifest: `trek-plugin.json` (id, permissions, egress). Type: `page` plugin — it renders as a wizard page inside TREK, not a widget.

## Repo layout — read this before assuming structure

This is an unusually flat repo — **do not expect a src/ tree, a bundler, or per-module files**:

- `server/index.js` — the *entire* backend. One `definePlugin({ onLoad, routes })` call with all route handlers and parsing/import logic written inline (no separate parser modules, no `require`d local files).
- `client/index.html` — the *entire* frontend, one file. CSS, vendored libraries (JSZip v3.10.1, exifr, and pdf.js v2.16.105 legacy build — all minified and pasted inline as `<script>` blocks), and the app's own vanilla ES5-style JS (`var`, no framework, no JSX/TSX). No build step produces this file — it's edited directly. **Every vendored library must be inlined, not shipped as a separate file** — see the CORP gotcha below; this was tried and confirmed broken.
- No `tsconfig.json`, `.eslintrc`, test framework, or build config exists anywhere in the repo. No `client/package.json` or `server/package.json` — the root `package.json` (with `trek-plugin-sdk` as sole devDependency) is the only manifest.

Vendoring client libraries (instead of npm+bundle) is deliberate: the client runs in a sandboxed, egress-restricted iframe (only `nominatim.openstreetmap.org` is allowed per `trek-plugin.json`), so it can't load anything from a CDN at runtime.

### Confirmed gotcha: a plugin's own bundled files can't be loaded via `<script src>` — CORP blocks it

The client-bridge docs describe an "own-path" CSP source that allow-lists the plugin's own `client/` files in `script-src`, implying a multi-file bundle (`<script src="./pdf.worker.js">`, etc.) should work with no inlining needed. **In practice, against a real TREK instance, this fails**: the iframe runs at an **opaque origin** (sandbox without `allow-same-origin`), so *any* `<script src>` fetch — even to the plugin's own same-path asset — is blocked by the browser as cross-origin at the network layer: `net::ERR_BLOCKED_BY_RESPONSE.NotSameOrigin`, despite the request itself returning **200 OK**. CSP `script-src` allowing the path doesn't help, because this is a separate browser mechanism (`Cross-Origin-Resource-Policy`), not a CSP check. This was hit firsthand while vendoring pdf.js as `client/pdf.min.js` + `client/pdf.worker.min.js` — the pattern only started working once **both files were inlined** as `<script>…</script>` blocks directly in `index.html`, exactly like JSZip/exifr already were. **Lesson: any new vendored library must be fully inlined, never referenced via `<script src="./…">` or any other relative-path asset fetch, regardless of what the CSP docs imply is possible.**

pdf.js additionally needs a Worker, and a `blob:`-URL worker would violate CSP (`worker-src` isn't declared, so it falls back to `script-src 'self' 'unsafe-inline'`, which doesn't cover `blob:`). The fix: inline **both** `pdf.js` and `pdf.worker.js` as plain `<script>` tags with no `GlobalWorkerOptions.workerSrc` set at all. pdf.js's UMD worker bundle, when executed as an ordinary script (not `require`d, no AMD), assigns itself to `globalThis.pdfjsWorker`; pdf.js's own worker-init code checks for that global *before* it ever needs `workerSrc`, and if found, uses it directly as a "fake worker" running on the main thread (no `new Worker()`, no second fetch, no CSP/CORP exposure at all). Confirmed against the actual vendored bytes via a Node `vm` sandbox emulating a bare `<script>` execution context (no CommonJS): the fake-worker path engages and `getTextContent()` returns correct text. This is fine for the small (1–3 page) PDFs this plugin parses; don't reach for a real Worker here.

## Commands

There are **no npm scripts** defined in this repo. Development workflow is entirely through the `trek-plugin-sdk` CLI (the sole devDependency), invoked directly:

```
npx trek-plugin-sdk dev       # local dev/hot-reload against a TREK instance
npx trek-plugin-sdk validate  # validate trek-plugin.json + permissions
npx trek-plugin-sdk pack      # package for the TREK-Plugins registry
```

There is no build, lint, or test command — there is nothing to compile and no test suite. Use the `trek-plugin-dev` skill for the manifest schema, the `ctx` API surface, the sandboxed postMessage bridge contract, and TREK-Plugins registry CI gates.

## Architecture

### Client/server split of labor

Anything requiring browser-only APIs (ZIP unpacking, EXIF reading, image compression, FileReader) happens **client-side**; all text/JSON *interpretation* happens **server-side** via `invoke()` calls to the plugin's own routes. This keeps `server/index.js` pure-JS with no zip/exif dependencies.

### The import pipeline (upload → detect → parse → preview → import)

1. **Detection** (`doAnalyze()` in `client/index.html`): dropped files are bucketed purely by extension (`.zip`, `.json`, `.pdf`, `.txt`/`.eml`, images, `.csv`/`.tsv`).
2. **Polarsteps ZIP**: unzipped client-side with JSZip; any `trip.json` found becomes a candidate (supports multiple trips per ZIP) → sent to `POST /parse-polarsteps`.
3. **Google Timeline JSON**: `parseGoogleTimeline` on the server handles three schema generations (`semanticSegments`, old `timelineObjects`, raw `locations`), then clusters points via `clusterByProximity` (haversine, 500m radius).
4. **Photos**: GPS EXIF extracted client-side via exifr → `POST /parse-gps`. Buckets by date, then **clusters by proximity within each day** (`clusterByProximity`, 500m radius — same helper `parse-timeline` uses) rather than collapsing a whole day to one median point. A single median-per-day was a real, user-reported bug: a day with photos from multiple distinct attractions produced exactly one point, sometimes landing nowhere real (independently-computed median lat + median lng doesn't have to correspond to any actual visited location) — confirmed against real data (user's manual EXIF check found 42 distinct coordinates; the old code produced 7, one per calendar day, regardless of how spread out that day's photos actually were). Each cluster becomes its own place with its own `date`/`lat`/`lng`/`photoCount`, so one calendar day can now legitimately produce several places. Deliberately does **not** carry over `clusterByProximity`'s generic `.name` (which would be a photo's filename, useless as a place name and would wrongly suppress the downstream `/import` reverse-geocode step, which only geocodes when `cluster.name` is falsy).
5. **Bookings**: `.pdf`/`.txt`/`.eml` all feed the **same** text pipeline. PDFs are read client-side with pdf.js (`extractPDFText()` → `getDocument().getPage().getTextContent()`, capped at 20 pages, 15s timeout per file) and their text is concatenated alongside `.txt`/`.eml` content, then sent to `POST /parse-bookings` — a regex-first extractor (`parseBookingsRegex`) with an opt-in AI fallback (`POST /parse-bookings {useAI:true}` → `ctx.ai.complete(BOOKING_PROMPT + text)`) that only fires if regex found nothing, surfaced as a "✨ Try AI assist" button. There is still no `ctx` API to drive TREK's own server-side PDF booking parser from a plugin (isolated child process, no session/REST access to core) — that's *why* extraction has to happen this way rather than by proxying to TREK's parser. Separately, the **original PDF file** is always attached to the trip too (`POST /import-pdf-booking` → `ctx.files.create`) as a backup for reference, regardless of whether text extraction found a recognizable booking.

   `parseBookingsRegex` has a **dedicated structured detector for multi-leg rail e-tickets** (SJ/Resplus-style exports, and likely similar layouts from other European rail operators): it matches repeating `HH:MM  From Station  HH:MM  To Station  Train NNNN` blocks, attaches the nearest preceding written-out date ("17 July 2026" / "17 juli 2026" — see `MONTH_NAMES`/`parseWrittenDate`, English + Nordic month names), dedupes identical legs (the same physical leg often repeats once per co-traveller's ticket in the extracted text), and returns one `type: 'train'` booking **per leg** — this runs *before* flight detection specifically because a service number like "SJ 3000" would otherwise false-match the `[A-Z]{2}\d{3,4}` flight-number pattern. A looser single-row fallback (unicode-aware `routePat`, requiring 1-3 Title-Case words on each side of a `-`/`–`/`to`/`→` separator, anchored to a field boundary so it doesn't swallow filler text or a stray hyphen from a reference number) covers other bus/train formats that don't have the `Train NNNN` marker, at lower confidence. `parseLocalizedNumber()` handles European price formats ("1 978,00") alongside US/UK ones.
6. **Expense CSV**: read client-side as text → `POST /parse-csv`, a hand-rolled quote-aware CSV/TSV parser with fuzzy header matching and keyword-based category detection. Amount parsing goes through the same `parseLocalizedNumber()` as booking prices (was previously a naive `parseFloat(strip-non-digits)`, which silently turned "20,00" DKK into 2000 by treating the decimal comma as a thousands separator — a real bug hit in production, not hypothetical). Currency comes from a detected CSV column when present; **when the CSV/booking text has no currency at all, the fallback is the user-selected `options.defaultCurrency`** from the Configure step's currency `<select>` (`#opt-currency`), not a hardcoded one — a trip can genuinely span multiple currencies (e.g. Sweden + Denmark), so `prepareStep3()` only *pre-selects* a best guess (majority vote across any currencies actually detected in `parsed.expenses`/`parsed.bookings`) and leaves the final call to the user.
7. **Preview**: one card per source type; individual rows are toggleable (`_selected`) — this selection state is what's actually sent to `/import`.
8. **Import** (`POST /import`, the orchestrator): creates or links the trip, then sequentially processes journal entries, places (deduped/clustered, reverse-geocoded via Nominatim), bookings (→ `ctx.accommodations.create` for hotels with valid check-in/out dates, else `ctx.reservations.create`), and costs.

### Trip day rows must be created explicitly — nothing does it for you

Neither TREK (as far as any available doc states) nor this plugin auto-creates day rows spanning a trip's start/end date when a plugin calls `ctx.trips.create` — confirmed by the fact that `ctx.days.create` was never called anywhere in this file until this was fixed, yet `ctx.trips.getDays` was relied on everywhere to build `dayMap`. The practical symptom: places/journal entries/costs all "imported successfully" (they exist as records) but never actually landed on a day in the trip planner, because `dayMap[date]` was silently `undefined` for a brand-new trip. `/import` now has its own gating section (before journal/places/bookings/costs) that computes the trip's date range — `tripConfig.startDate/endDate` → Polarsteps dates → `ctx.trips.getById` (existing trip) → the min/max date actually found across the imported data, in that order — and calls `ctx.days.create` for any missing day in range, capped at 400 days (a single bad/placeholder date, e.g. a "no end date" sentinel like `2099-01-01`, was confirmed to otherwise balloon the range to tens of thousands of days and burn the entire budget on that one section forever). **This section must fully finish (all days in range created) before journal/places/bookings/costs are allowed to run** — letting them start against a partially-built `dayMap` would silently and permanently skip day-assignment for items whose date's day hadn't been created yet (indices are never revisited once consumed).

**The trip's own declared start/end date is not guaranteed to cover every date in the imported data — and originally, the range computation only fell back to the data's own span when the trip had NO declared range at all.** Since a Polarsteps trip (or an existing TREK trip) almost always *does* have a start/end date, that fallback essentially never triggered for the most common case — meaning any GPS photo or Google Timeline point dated even one day outside the Polarsteps-reported window (a travel day before/after the recorded trip, a timezone-edge date) had no day row to be assigned to: `dayMap[cluster.date]` was `undefined`, so `itinerary.assign` silently no-opped. The place still got created — it just never appeared on any day, which is what "places aren't showing up on the itinerary" actually meant in practice, independent of the clustering issue below. Fixed by changing the range computation to always **extend** `rangeStart`/`rangeEnd` to cover every well-formed date found across `steps`/`gpsPlaces`/`timelinePlaces`/`bookings`/`expenses`, on top of whatever official range was already known, rather than only using the data's span as a total fallback. The 400-day sanity cap still applies on top of the extended range. Note this only widens which day *rows* get created server-side for assignment purposes — it does not update the trip's own displayed `start_date`/`end_date` metadata in TREK.

Separately — and easy to miss even once day rows exist — **linking a place to a journal entry (`entry.place_id`) is not the same as putting that place on the trip's day/itinerary view.** The Polarsteps journal loop creates a place per step and attaches it to the journal entry, but was never calling `ctx.itinerary.assign(tripId, dayId, placeId)` — so those places existed and were journal-linked, yet never appeared in the day-by-day itinerary. (The separate GPS/timeline places section already called `itinerary.assign` correctly — only the Polarsteps path was missing it.) Any future place-creation path needs both: attach to whatever entity makes sense (journal entry, booking, etc.) *and* `itinerary.assign` it to the day, if a day for its date exists.

**Even with `itinerary.assign` being called correctly, `clusterByProximity()` itself was silently starving it of a date to assign to.** The merge predicate only ever checked distance — once two points landed in the same cluster, the cluster kept whichever `date` its *first* member happened to have, and never updated it as more members merged in. Two concrete failures came from this: (1) if the first-processed point in a cluster had no date (an EXIF-dateless photo), the whole merged place stayed dateless forever even if later members did have real dates, so `cluster.date && dayMap[cluster.date]` (in `/import`'s GPS+Timeline places section) failed and `itinerary.assign` never ran; (2) `/parse-timeline` clusters a trip's *entire* location history in one global pass with no per-day bucketing (unlike `/parse-gps`, which buckets by day first) — so any real-world location visited more than once (a hotel, a home base) collapsed into a single cluster carrying only one visit's date, silently dropping the itinerary link for every other visit. Fixed by making the merge predicate require `!c.date || !p.date || c.date === p.date` (distance alone no longer merges two differently-dated points) and having a cluster adopt a member's date if it didn't have one yet. Any future clustering call site should assume `clusterByProximity()` now preserves day granularity by design — don't reintroduce a plain distance-only merge for place data that needs per-day itinerary assignment.

The `/import` fallback above only kicks in server-side, and only for sizing day-row creation — it never touches `tripConfig.startDate/endDate` themselves, so a bookings/photos/expenses-only import (no Polarsteps `trip.json`) would otherwise create the trip record itself with `start_date`/`end_date` both `null`. `prepareStep3()` in `client/index.html` now covers this earlier, client-side: if there's no Polarsteps trip (or it has no dates) and the user hasn't already typed dates into `#trip-start`/`#trip-end`, it takes the same min/max-across-sources approach (scanning `parsed.bookings` `from_date`/`to_date`, `parsed.gpsPlaces`/`parsed.timelinePlaces` `date`, `parsed.expenses` `date`) and pre-fills both fields, showing a `#date-detect-hint` note telling the user the range was inferred and to double-check it before importing. This is a separate, independent computation from the server's — the client one sets what actually gets sent as `tripConfig.startDate/endDate` (and thus the trip's real `start_date`/`end_date`), while the server one only bounds which `ctx.days.create` calls happen.

**Every date fed into either min/max computation must already be a clean `YYYY-MM-DD` string, or both silently break.** This was hit for real: booking-only imports auto-detected dates correctly, but adding an expense CSV or GPS photos on top made detection stop working entirely. Root cause — two sources weren't actually normalized despite looking like they were: `/parse-csv`'s expense `date` field was the **raw CSV cell**, unparsed (no equivalent of `parseLocalizedNumber()` for dates existed until `normalizeDateStr()` was added); and `/parse-gps` bucketed EXIF-dateless photos under the **literal string `'unknown'`** and then let that leak straight into the place's own `date` field instead of keeping it as an internal-only grouping key. Both plain `Array.sort()` calls (client and server) sort lexicographically, so one `"unknown"` or one `"16/07/2026"` mixed in with real `"2026-07-16"`-style strings reliably wins or corrupts the min/max — and assigning a non-ISO string to an `<input type="date">` is a silent no-op in the browser, so the visible symptom was an *empty* field with no error, not a wrong-looking one. Fixed by adding a shared `normalizeDateStr()` (server) for the CSV date column, making `/parse-gps` emit `null` instead of `'unknown'` for undated photos, and — as defense in depth against any future source that isn't fully normalized — both min/max computations (`/import`'s server-side fallback and `prepareStep3()`'s client-side fallback) now filter with `/^\d{4}-\d{2}-\d{2}$/` before sorting, rather than trusting every upstream field to already be clean. Any new date-bearing source must emit ISO `YYYY-MM-DD` or `null` — never a raw/loose string or a sentinel placeholder — or it'll reintroduce this exact failure mode.

There are no shared type/schema files between client and server — object shapes (e.g. the booking shape `{type, title, from, from_date, ...}`) are implicit JSON contracts kept in sync by hand between `server/index.js` and `client/index.html`. When changing a field name or shape, grep both files.

### `/import` is index-resumable — real per-call ceiling is ~8s, not the documented 30s

The `trek-plugin-dev` skill documents a 30s server-side route timeout, and that's real — but it is **not** the actual constraint on this route. **Confirmed against a real instance**: TREK's own `trek:invoke` bridge in the browser enforces its own **~8-second round-trip timeout**, independent of and much shorter than the route's 30s execution budget. Symptom: the client showed `Import failed: timeout of 8000ms exceeded` while the server-side route was likely still well inside its own 30s allowance. Nothing in the SDK docs mentions this; treat it as a hard fact about this TREK instance, not a documentation gap to double-check away.

Reverse-geocoding is rate-limited to ~1/sec, so at most a couple of geocoded items fit under an 8s ceiling — for any non-trivial trip (many Polarsteps steps, many distinct GPS-photo dates, many bookings/costs), **a single `/import` call finishing everything is the exception, not the norm**. Rather than push that back onto the user as "click Import again," `/import` is **index-resumable**:

- Request carries an optional `progress` object: `{journeyId, journal, journalEntries, journalDayNotes, places, placesCreated, bookings, bookingsRes, bookingsAcc, bookingsReview, costs, costsCreated, done}`. The four `*Idx`-style fields (`journal`/`places`/`bookings`/`costs`) are **the next array index to process** for that section — every per-section loop is a plain indexed `for` (not `for...of`) that `break`s (not `continue`s) on `!withinBudget()`, so it can report exactly where it stopped.
- The journal section creates its `ctx.journal.createJourney` **once** (when `progress.journeyId` is falsy) and reuses the id on every resumed call — a naive rewrite that re-creates the journey per call would silently produce one near-empty journey per round.
- The "places" section recomputes `clusters` fresh **every call** from `gpsPlaces`/`timelinePlaces`/`polarsteps` — safe only because the client always resends those arrays unchanged across rounds, so the same deterministic computation reproduces the same array and `progress.places` stays a valid index into it.
- Response returns the updated `progress` (with `done: true` once every active section's index has reached its array's length) alongside `log` (**cumulative** totals, safe to just redisplay each round) and `errors` (**per-round only** — the per-item failures from whatever was processed in *this* call; must be accumulated client-side, not overwritten).
- **No item is ever re-attempted once its index has been consumed** — this is what makes resuming safe instead of duplicating. Any future section added to `/import` needs the same indexed-loop-with-reported-stop-index treatment, or resuming it will either duplicate work or skip it.

`doImport()` in `client/index.html` loops calling `/import`, feeding each response's `progress` back in as the next call's input and switching `tripConfig` to `{mode:'existing', tripId}` after the first call, until `progress.done` (capped at 200 rounds as a runaway backstop). `result.log` messages are redisplayed as-is each round (cumulative); `result.errors` are concatenated across rounds into `allErrors`. `setProgUpdate()` (spinner, not checkmark) is used for a section's UI row until the round where `progress.done` is true, at which point `setProgDone()` (checkmark) takes over — except the `'trip'` row, which checkmarks immediately since trip creation/linking always completes in the first round.

`reverseGeocode()`'s own per-call timeout is 2500ms and `/import`'s deadline is `Date.now() + 6000` — both sized for the ~8s bridge ceiling, not the 30s route ceiling. **`withinBudget()` only gates whether a *new* item starts, it can't interrupt one already in flight** — this is why `reverseGeocode()` needs its own bounded `AbortController` timeout rather than relying on the shared deadline alone; any future per-item operation that makes an external call needs the same treatment.

### Error-handling convention

Every route handler is wrapped in `tryAttempt()` + `safeJson(200, ...)`, so the client's `invoke()` promise always resolves (never rejects) even on expected failures — errors surface as `{error: message}` in a 200 response, not an HTTP error status. Inside batch loops (`/import`), each item is individually try/caught into a local `errors[]` array so one bad item doesn't abort the rest of the batch.

### Client postMessage bridge — two parallel implementations, only one is live

`client/index.html` contains **two** separate `postMessage`/`invoke()` implementations:
1. A full "TREK plugin design kit" bridge (~lines 324-633) exposing `window.trek.invoke()`, theme/context application, auto-enhanced `<select>`s.
2. A second, simpler `invoke()`/message-listener pair defined again in the app's own script (~lines 871-884).

**The app logic calls the second (`invoke()`), not `window.trek.invoke()`.** Both listeners independently key off `requestId` so they don't conflict, but this is duplication to be aware of — don't assume `window.trek.invoke()` is what's driving the wizard.

### Confirmed: the plugin-route body-size ceiling is `express.json({limit:'100kb'})` — not a guess anymore

For a long time this was documented as "undocumented, presumably a body-size limit on the plugin-route proxy." It's now confirmed from TREK's own source (`liketrek/TREK` — the project moved from `mauriceboe/TREK` to its own GitHub org; old links still redirect): `server/src/middleware/globalMiddleware.ts` sets a global `app.use(express.json({limit:'100kb'}))`, and `server/src/nest/plugins/plugins-proxy.controller.ts` (the controller that dispatches every plugin route call) forwards `req.body` straight through with no override — so this applies to **every** plugin route, no exceptions. `100kb` here is the `bytes` package's 1024-based unit: **102,400 bytes for the entire JSON request body**, not just a base64 payload — `tripId`/`filename`/`mimetype`/`description`/etc all share that same budget.

Both earlier guesses at this number (900KB, then 250-300KB after a real 413) were still far above the real ceiling. `PDF_ATTACH_MAX_BASE64`/`PHOTO_UPLOAD_MAX_BASE64` are now 85KB, and `compressUnderCap()`'s shrink-retry ladder gained two more aggressive passes (`[250,0.3]`, `[150,0.25]`) to reliably land under the real target instead of the old guessed one. PDFs still can't be recompressed, so `/import-pdf-booking`'s guard is just a lower skip threshold — the booking itself already made it in via the text pipeline regardless, so this only affects the backup file attachment; realistically most multi-element PDFs will still exceed 85KB and get skipped, which is now an accurately-documented reality rather than an occasional surprise.

**These caps must be compared against the base64 STRING length directly, not a decoded/raw-byte estimate — a real 413 in production, even after the "fix" above, was this exact confusion.** Both `compressUnderCap()` and the PDF-attach check used to compute `Math.round(b64.length*0.75)` (converting the base64 string back down to an estimate of the *raw* decoded bytes) and compare *that* against the cap — meaning a pass that "fit under 90KB" by this check was actually producing a base64 string up to 4/3 (33%) **larger** than 90KB, since `*0.75` goes the wrong direction for a size-limit check on the string that's actually transmitted. A 90KB-by-this-broken-check photo could genuinely be a ~120KB base64 payload — comfortably over the real 100KB limit despite the check reporting success. Fixed by comparing `b64.length` directly against the cap in both places; `sizeBytes` (still `*0.75`, decoded-byte estimate) is kept only for logging/display, never for the size gate itself. **Any future size-capping code here must cap `b64.length`, never a `*0.75`/`*4/3`-transformed value** — the whole point of `*0.75` is to convert base64 length into an estimate of something *else* (the raw bytes), which is the wrong direction when the thing actually being capped is the base64 string itself.

**This same 100KB ceiling turned out to be a much bigger problem than just file uploads — see the next section.**

### `/import`'s own JSON payload can exceed 100KB for a large trip, independent of the 8s time budget

The index-resumable design (previous section) solves the ~8s *execution-time* ceiling by processing a slice of work per round. But for a long time, every round still resent the **complete** `polarsteps.steps`/`bookings`/`expenses`/`gpsPlaces`/`timelinePlaces` arrays — deliberately, so the server could recompute GPS/timeline clustering deterministically from the same full input every call. Once the real 100KB body-size ceiling above was confirmed, this became a second, independent failure mode: a request could 413 **before the route handler even runs**, no matter how small the per-round execution budget is.

Measured against realistic data: a trip with **~100-150 combined items** (Polarsteps steps + expense rows + GPS clusters) already produces a >100KB request — not a rare edge case, but exactly the shape of trip this plugin's "import as much past data as possible" goal targets (a multi-month Polarsteps trip easily has 100+ stops; a detailed expense CSV easily has 100+ rows). Confirmed independently from a real instance too: even a single 300-step `trip.json` alone (~0.27MB) 413s in one `/parse-polarsteps` call, well below what local `trek-plugin dev` testing can ever catch (the dev server doesn't enforce whatever the production proxy does).

The fix has two parts, and **both were needed** — one alone doesn't cover every source:

1. **Windowed pagination for `polarsteps.steps`/`bookings`/`expenses`** (steps chunking for `/parse-polarsteps` and `/import` was already built independently before this was written up; bookings/expenses pagination was added to match). Each large source is stripped from the base `importBody` and instead injected as a rolling window each round (`STEPS_PER_ROUND`/`BOOKINGS_PER_ROUND`/`EXPENSES_PER_ROUND` = 40), sliced client-side from `progress.journal`/`progress.bookings`/`progress.costs` — the same indices the server already reports back every round. A source at or under its own per-round cap is still sent whole every round, unchanged. Server-side, each section reads a matching `<source>Offset`/`total<Source>` pair (e.g. `stepOffset`/`totalSteps`, `bookingsOffset`/`totalBookings`) to re-base the received slice back onto the correct global index — absent (an older/unpaginated call) defaults to "this is everything, starting at 0", so the shape is backward compatible.
2. **GPS/timeline clustering moved client-side** (`computeTargetPlaces()`, using `clusterByProximity()`/`haversine()` ported into `client/index.html` verbatim from `server/index.js`, including the 1.6.3 date-preservation fix). Plain windowed pagination doesn't work for `gpsPlaces`/`timelinePlaces` the way it does for steps/bookings/expenses, because clustering needs to see every point together to merge correctly — chunking the *raw* points per round would split points that should merge into the same cluster across different rounds and never merge them. Computing the deduplicated, clustered `places` list **once**, client-side, before the resumable loop starts sidesteps this: only the (usually much smaller) *result* needs to be paginated, using the same offset/total pattern as everything else (`placesOffset`/`totalPlaces`). The server still knows how to cluster from raw `gpsPlaces`/`timelinePlaces` itself as a fallback when `places`/`totalPlaces` are absent, but the client no longer sends the raw arrays at all.

**Day-range extension needed a third fix to stay correct under pagination.** Section 1.5's date-range computation (previous "Trip day rows" section) scans `steps`/`bookings`/`expenses`/`gpsPlaces`/`timelinePlaces` for dates to extend the day-creation range — but once these arrive as partial per-round windows, that scan only ever sees the *current* round's slice, and could under-extend the range for a large trip. The real fix is `extendDateRange()` (client-side, `client/index.html`): computed once per target from the **full** in-memory data (before any pagination), it widens `tripConfig.startDate`/`endDate` to cover every date across steps/bookings/expenses/computed-places, so the first request already carries the fully-correct range. The server's own array-scanning version of this stays in place as defense-in-depth only, not the source of truth, now that it can't see everything at once.

**A regression of the original 1.6.4 day-range-extension fix was found and re-fixed while working on this.** At some point between 1.6.4 and 1.13.0 (during independent work this session has no visibility into — most likely the 1.6.4→1.10.0 gap), the range computation had silently reverted to the pre-1.6.4 pattern (`if (!rangeStart || !rangeEnd) { ...fallback... }` — only extending when the trip had **no** declared range at all, not always). Since a Polarsteps trip almost always has a declared range, this fallback essentially never fired, reintroducing the exact "GPS/timeline points outside the Polarsteps window never get a day row" bug 1.6.4 already fixed once. Re-confirmed via `git show <commit>:server/index.js` across several historical commits and re-applied. **If this section ever looks like a simple `if` gate again, it's wrong — it must always extend, never just fall back.**

**A more severe bug — a live `ReferenceError` breaking every Polarsteps journal import — was also found and fixed in the same pass.** The independently-built steps-pagination work (item 1 above) referenced `stepOffset`/`totalSteps` throughout both the journal-only and normal `/import` code paths, but never actually **defined** either variable anywhere in `server/index.js`. Since the file has `'use strict'`, this threw immediately whenever `journalActive` was true — i.e. on every single Polarsteps journal import, paginated or not. Fixed by deriving both from the paginated `polarsteps` object wherever `const steps = polarsteps?.steps || []` is declared: `const stepOffset = polarsteps?._stepOffset || 0` and `const totalSteps = polarsteps?._totalSteps ?? (stepOffset + steps.length)` (the fallback makes an unpaginated call behave as "this is everything, starting at 0"). The journal-only code path also had its loop indexing wrong in the same spot (`for (; i < steps.length; i++)` instead of `for (; i < stepOffset + steps.length; i++)`, `steps[i]` instead of `steps[i - stepOffset]`) — a global progress index compared/looked-up against a local per-round slice, which would have silently stopped processing after the first round for any paginated journal-only import. **Lesson for anyone extending this pattern to a new source: `grep` for every use of the source's own `.length` and index after adding offset/total fields — a partial migration throws or silently misbehaves, it doesn't fail loudly at the call site that's actually wrong.**

### Getting imported photos into the Journey view: not via `ctx.journal`, but via the `photoProvider` hook

TREK's own Journey/journal feature (`ctx.journal.createJourney`/`createEntry`) renders each entry with its own `photos[]` gallery (`photo_id`, `provider`, `asset_id`, `file_path`, `thumbnail_path`, `width`, `height`) — confirmed via a real `GET /api/journeys/:id` response where most entries already carried `provider: "immich"` photos with real Immich asset ids. **There genuinely is no way to write directly into that gallery.** Every photo this plugin uploads (`/upload-photo`, both the per-target photo loop and the Polarsteps step-photo loop in `doImport()`) goes through `ctx.files.create()` — which attaches a generic file to the trip's **Files** tab (optionally linked to a place via `place_id`), a completely different system from journal-entry photos. `ctx.journal` only exposes `createEntry`/`updateEntry`/`deleteEntry`/`createJourney`/`deleteJourney`, none of which accept a photo/file reference — confirmed against TREK's actual `plugin-sdk/src/index.ts` types, not just the `trek-plugin-dev` skill's docs. The `provider: "immich"` photos already showing up are unrelated to this plugin — they're TREK's own native Immich-library integration, independent of anything imported here.

The real fix turned out to be the **`photoProvider` hook** (`hook:photo-provider`), implemented below `routes` in `definePlugin()`. Initially dismissed as a dead end because TREK's own admin permission-grant screen lists a *different* hook, `hook:journal-entry-provider`, with the hint "Contribute entries to a journey" — sounds relevant, but reading the actual interface (`JournalEntryProvider.getRows(entryId, ctx): Promise<{label,value?,url?}[]>`) shows it's read-only display augmentation (extra info rows shown under an *existing* entry, same shape as `PlaceDetailItem`), not a way to create entries or attach photos — TREK's own UI hint text oversells what it does. `photoProvider` is the one that actually matters:
```ts
interface Photo { id: string; title?: string; thumbnailUrl: string; fullUrl: string; takenAt?: string; }
interface PhotoProvider {
  search(query: string, opts: {page,limit}, ctx): Promise<{photos: Photo[]; total: number; hasMore: boolean}>;
  getById(id: string, ctx): Promise<Photo | null>;
}
```
Confirmed via TREK's real `plugin-photos.controller.ts`: this is "surfaced in the photo picker... the picker fans these into its 'plugin sources' tab" — i.e. every photo this plugin has ever uploaded becomes searchable and pickable directly from TREK's native photo picker, including (per that same picker) when adding a photo to a journal entry. The user picks it themselves through TREK's own UI; this plugin never touches the journal entry's photo record directly — but that's enough to get imported photos in front of the Journey view, which `ctx.journal`'s own methods can't do at all.

Two things this took actual source-reading (not just the skill's docs) to nail down, both confirmed by fetching the real TREK GitHub source via `gh api repos/mauriceboe/TREK/contents/...`:
- **Hooks are not gated by manifest `type`.** `plugin-supervisor.ts`'s `providersOf(hook)` only checks `sup.status === 'active' && sup.hooks.includes(hook) && sup.granted.has(perm)` — no `type` check anywhere. So this plugin keeps `type: "page"` and simply adds a top-level `hooks` object alongside its existing `routes`; no restructuring needed.
- **`thumbnailUrl`/`fullUrl` must be absolute `http(s)://` URLs** — the controller validates with `new URL(raw).protocol`, which throws (silently dropping the photo) on a relative path. `ctx.files.create()`/`list()` already return a relative `url` field (`/api/trips/<tripId>/files/<fileId>/download`, confirmed in `fileService.ts`'s `formatFile()`), and that download route "accepts a cookie, a Bearer header OR a one-shot `?token=` param" (confirmed in `files-download.controller.ts`) — so a plain `<img>` tag rendered inside the user's own logged-in TREK tab loads it fine via the existing session cookie. The one piece a plugin can't discover on its own is TREK's own public base URL (nothing in `ctx` exposes it), so there's now a `trek_base_url` setting (`trek-plugin.json`'s `settings[]`) used to turn that relative `url` into an absolute one — mirroring exactly why TREK's own `APP_URL` env var exists for OIDC. **Deliberately `scope: 'user'`, not `'instance'`** — this instance's admin doesn't expose instance-scoped plugin config, so each user fills in their own value under their personal Settings instead, read server-side via `ctx.settings.get('trek_base_url')` (the acting user's own decrypted value — not `ctx.config`, which only ever surfaces `scope:'instance'` fields). Left unset for a given user, `search()`/`getById()` both return nothing for them rather than emitting URLs TREK would just drop anyway.

`search()`/`getById()` scan the acting user's own trips (`ctx.trips.listMine()`, capped at 25) and each trip's files (`ctx.files.list()`, capped at 200/trip), filtering to `mime_type` starting with `image/`. Bounded on both axes deliberately — this hook has a hard **5-second host-side timeout** (confirmed in `plugin-photos.controller.ts`'s `invokeHook(..., 5000)`), tighter even than `/import`'s already-tight budget. `db:read:files` had to be added to `permissions` for this (previously only `db:write:files` was declared — creating/uploading files doesn't imply being able to list them back).

### Polarsteps import mines more of `trip.json` than it used to — six specific additions

The Polarsteps step/trip shape returned by `/parse-polarsteps` and consumed by `/import` was, for a long time, minimal — several fields Polarsteps actually provides were parsed and then silently dropped, or never read at all. All confirmed against a real `trip.json` sample (note the trip-level steps array is `trip.all_steps`, not `trip.steps` — an easy field-name trap):

- **Timezone-aware step dates**: `unixToDate()` always converts a Unix timestamp to a UTC calendar date. Polarsteps step timestamps are UTC epoch seconds, but each step also carries its own IANA `timezone_id` (e.g. `"Asia/Shanghai"`) — a step that happened late at night locally but crosses midnight in UTC was silently assigned to the **wrong calendar day**, cascading into wrong day-row/itinerary assignment. Fixed with `unixToDateInTz(ts, tz)`, which uses `Intl.DateTimeFormat('en-CA', {timeZone: tz, ...})` (the `en-CA` locale conveniently formats as `YYYY-MM-DD` directly) and falls back to plain UTC if `tz` is missing or an invalid IANA name (the constructor throws on those). Node ships full ICU by default, so no new dependency was needed.
- **Trip cover photo**: `trip.cover_photo_path` (Polarsteps' own "large_thumb" rendition) is fetched server-side in `/import`'s trip-creation section and passed to `ctx.trips.update(tripId, {cover_image: 'data:...;base64,...'})`, best-effort. **The exact shape `cover_image` expects isn't documented** beyond the permission name (`trip_cover_upload`) — a data URI was chosen as the closest match to how every other upload in this plugin works, but this is unconfirmed against a real instance and wrapped so a wrong shape/failed fetch never blocks the rest of the import.
- **Trip summary**: `trip.summary` (the user's own free-text trip narrative) was parsed nowhere. Now surfaced as a "Trip overview" journal entry, created exactly once alongside the journey itself (piggybacked on the existing `!journeyId` one-time guard — no separate progress flag needed, since that block already only ever runs on the first resumed round).
- **Multi-day steps**: `step.end_time` was never read, so a multi-day stay (e.g. a week in one city) only ever got assigned to its *start* date — every other day of the stay showed nothing on the itinerary. `/parse-polarsteps` now also returns `endDate` (timezone-aware, only set when genuinely later than `date`), and `/import`'s step loop assigns the same place to every day in that range (capped at 60 days per step as a sanity limit, mirroring the trip-wide 400-day cap — this runs inside a single step's own iteration, not as its own resumable section, so an implausible span could still eat into that round's budget).
- **Step photo CDN fallback**: `step.main_media_item_path` (a direct Polarsteps CDN URL for a step's own designated photo) was parsed nowhere, even though it's genuinely useful for a **bare `trip.json` import with no full ZIP export** (so there's no local photos-folder at all). Implemented **client-side**, not server-side: the iframe's CSP `connect-src` is built from this plugin's own granted egress hosts (see `client-bridge.md`'s isolation model), and `polarsteps.s3.amazonaws.com` is now one of them — so `doImport()` can `fetch()` the URL directly, reuse the existing `compressUnderCap()`/`/upload-photo` pipeline unchanged, and only do this for steps that got *no* local ZIP photo at all (checked via `target.stepPhotosByStepId[step.id]`), avoiding a redundant duplicate attachment when a full export is present.
- **Duplicate-import detection via `uuid`**: `polarsteps.uuid` was parsed and returned but never used. Now stored via `ctx.meta.set('trip', tripId, 'polarsteps_uuid', uuid)` the first time a Polarsteps trip is imported as a new trip. Before creating another new trip, `/import` checks existing trips' meta for a match (only on a genuinely fresh call — `!progressIn` — so it can't re-trigger mid-import once `tripConfig` has switched to `{mode:'existing'}`) and returns `{duplicateOf:{tripId,title}}` instead of creating anything. The client shows a `confirm()` prompt and, if the user proceeds anyway, resends with `tripConfig.forceDuplicate:true` to skip the check. Bounded to the first 200 of the user's trips (via `ctx.trips.listMine()`) as a sanity cap, and every `ctx.meta` call goes through the shared `attempt()` helper (silently swallows both a thrown rejection and the synchronous property-access throw an unavailable-on-this-host namespace raises) rather than hard-depending on it, per the `trek-plugin-dev` skill's own guidance that `ctx.meta` has been observed `undefined` on real hosts.

Both `db:write:trips` (for `ctx.trips.update`) and `http:outbound:polarsteps.s3.amazonaws.com` (+ matching `egress[]` entry) were newly added to `trek-plugin.json` for these features — any future change touching cover photos or CDN photo fetching should keep both permission lists in sync, same as the existing Nominatim egress entry.

### Journal-only mode: a standalone journey with no trip at all

`options.journalOnly` (checkbox `#opt-journal-only` in the Configure step, `toggleJournalOnly()` in `client/index.html`) is a genuinely different import shape, not a restricted subset of the normal one — it's for a user who just wants a travel story/journal from their Polarsteps data without engaging the full trip-planning machinery (no places, no calendar days, no itinerary, no bookings/costs). This only works because `ctx.journal.createJourney`'s `trip_ids` field is **optional** (confirmed against TREK's actual `plugin-sdk/src/index.ts` type: `trip_ids?: number[]`) — a Journey can exist with zero associated trips.

Server-side, `/import` branches on `options.journalOnly` right after building the resumable `progress` object (`server/index.js`, section "0. Journal-only mode"), *before* section "1. Trip" ever runs — no `ctx.trips.create`, no day-row section, no places/bookings/costs sections, since every one of those needs a `tripId` and none exists in this mode. It reuses the same `p.journeyId`/`p.journal`/`p.journalEntries`/`p.createdRefs` progress fields as the normal path (including the trip-summary intro entry from the Polarsteps-mining work above) and returns `tripId: null`. **The early "nothing to import" return must still set `progress.done: true`** — an earlier version of this returned the unmodified `p` object, which has no `done` field, so the client's resumable loop (which only stops on `progress.done`) would have silently resent the same no-op call up to its 200-round cap.

Client-side (`importOneTarget()`), journal-only mode reduces the progress-step list to just `journal` (skipping `trip`/`days`/`places`/`bookings`/`pdfbooks`/`costs` entirely) and forces every other "what to import" checkbox off+disabled via `toggleJournalOnly()`. The PDF-attach and photo-upload phases further down *already* guard on `result.tripId` being truthy, so they no-op automatically once `tripId` is `null` — no extra gating needed there. **`/undo-import` had to be changed to accept a missing `tripId`**: it used to hard-require one (`if (!tripId || !refs.length) return ...`), but `journalEntry`/`journey` deletes (`ctx.journal.deleteEntry(id)`/`deleteJourney(id)`) never took a `tripId` to begin with — only `place`/`reservation`/`accommodation`/`cost`/`file`/`daynote` refs are actually trip-scoped, so the route now only requires `tripId` for *those* ref types specifically. The client's own `doUndoImport()` had the identical bug (`batches.filter(b => b.tripId && ...)`, which would have silently excluded every journal-only batch from ever being undoable) — fixed the same way, by dropping the `tripId` truthiness requirement from the filter.

### Collection mode: importing places into a Collection instead of a Trip

`importMode` (`setImportMode()`, toggled at the very top of Step 1) is a second, almost entirely separate import target alongside the normal Trip flow — a **Collection** (`ctx.collections.*`) is a user-owned saved-place list with no trip, no dates, no days, no itinerary at all, closer in spirit to a Google Maps "saved places" list than to a trip plan. It shares the same 4-step visual shell (`step-1`..`step-4`) but runs almost entirely separate functions (`doAnalyzeCollection()`/`renderCollectionPreview()`/`prepareCollectionStep3()`/`doImportCollection()`), gated behind `importMode==='collection'` checks at the very top of `doAnalyze()`/`doImport()`/`goStep(3)` — deliberately, so the existing (well-tested) Trip flow's own functions stay untouched rather than growing conditional branches throughout.

The exact shape of `ctx.collections.*` came from reading TREK's actual source (not just the plugin-sdk's loosely-typed `Record<string, unknown>` signatures) — `shared/src/collection/collection.schema.ts`'s zod schemas gave the real field names: `ctx.collections.create({name})` → `{id, ...}`; `ctx.collections.savePlace({collection_id, name, lat, lng, address?, notes?, ...})` → `{place?, duplicate?, duplicateOf?}` (a **built-in dedup precheck** — a duplicate returns normally with `duplicate:true` rather than throwing, no `force:true` sent by this plugin so duplicates are always skipped rather than double-saved). `wiki/Plugin-Cookbook.md`'s one-line collections recipe confirmed the minimal call shape before the full schema file confirmed every field.

Three new sources feed Collection mode, all producing the same flat `{name, lat, lng, address?, notes?, date?}` shape with **no proximity clustering** (unlike GPS-photo/timeline points for a trip) — each entry here already carries its own distinct name, so clustering would wrongly merge two differently-named places that happen to sit near each other:
- **Google Maps Takeout "Saved Places" export** (`/parse-google-places`) — a GeoJSON `FeatureCollection`. **Unconfirmed against a real current export** — built from general knowledge of the format (no sample was available, only a live Google Maps share link, which redirects through a cookie-consent wall and isn't the same thing as a Takeout file anyway). At least two known property-naming variants exist across Takeout versions (lowercase `properties.location.{name,address,geo_coordinates}` vs capitalized `properties.Location["Business Name"/"Address"/"Geo Coordinates"]`); the parser tries several known paths and falls back gracefully. `geometry.coordinates` (plain GeoJSON `[lng,lat]`) is tried first for coordinates since it's the most likely field to stay stable regardless of which `properties` variant a given export uses. **Needs real-world testing against an actual export to confirm or correct.**
- **KML/KMZ** (existing `parseKMLText()`, already used for trip GPX/KML places) — reused as-is, just routed to `parsedCollection.places` instead of a trip target.
- **Generic place-list CSV** (`/parse-places-csv`) — fuzzy header matching (`name`/`lat`/`lng`/`address`/`notes`/`date`), mirroring `/parse-csv`'s expense-column matching but for place columns; a row with no recognizable lat/lng is skipped.

Server-side, `/import-collection` mirrors `/import`'s index-resumable shape (progress carries the next place index + running totals across rounds) and the same windowed-pagination pattern (`placesOffset`/`totalPlaces`, `PLACES_PER_ROUND=40` client-side) for the same reason: a large saved-places export can push the request past the confirmed ~100KB plugin-route body-size ceiling just as easily as a large trip can. A new collection is created **once** (guarded by `p.collectionId` already being set, exactly like `p.journeyId`/`p.tripId` elsewhere) and reused across resumed rounds. `/undo-import` gained a `collectionPlace` ref type (`ctx.collections.deletePlace(id)`, no `tripId` needed — same non-trip-scoped category as `journalEntry`/`journey`); the collection itself is never deleted by undo, matching the existing convention that trips/journeys aren't deleted either, only their contents.

New permissions: `db:read:collections` (list existing collections for the "add to existing" picker) and `db:write:collections` (create a collection, save places into it).

### Pasting a shared Google/Naver Maps list link directly (no export file needed)

A fourth Collection-mode source, alongside the Google Takeout GeoJSON/KML/CSV file-drop sources above: a text field in step 1 (`#collection-link-row`, shown only in Collection mode) where the user pastes a share link straight from Google Maps' or Naver Maps' own "Share list" button, no export step required at all.

This exists because **TREK's own core app already has this feature** — a native "List Import" (Google List / Naver List) that does the same thing against a trip, confirmed by reading the actual source (`server/src/services/placeService.ts`'s `importGoogleList()`/`importNaverList()`, `liketrek/TREK`, AGPL-3.0). The user pointed this out after being told a Google Maps share link couldn't be resolved server-side — a live test of the user's real share link confirmed a plain fetch does redirect through `consent.google.com` (a GDPR interstitial no plugin fetch can click through), but reading TREK core's own implementation showed **that's not how TREK does it either**: it never needs to interact with the consent page at all.

**The actual mechanism** (ported logic-for-logic, not code-for-code, into `/parse-google-list` and `/parse-naver-list` in `server/index.js`):
- For a `goo.gl`/`maps.app.goo.gl` short link, follow the redirect (`fetch(url, {redirect:'follow'})`, reading `res.url`) — but only far enough to get the **resolved URL string**, never rendering or interacting with the destination page. Even when that resolved URL is itself a `consent.google.com/ml?continue=<encoded-original-url>` interstitial, the list ID substring (`!2s<id>` or `placelists/list/<id>`) survives intact inside the `continue=` param, because `!` isn't URL-escaped by Google's own redirect construction — so a plain regex still finds it without ever loading that interstitial.
- That list ID is then handed to a **completely separate, unauthenticated internal Google Maps AJAX endpoint** — `https://www.google.com/maps/preview/entitylist/getlist?...&gl=us&pb=!1m1!1s<listId>!2e2!3e2!4i500!16b1` — the same call Google Maps' own web frontend makes to populate a list side-panel, not part of the consent-gated interactive page-view flow at all. `gl=us` on *this* endpoint (not the redirect) is what avoids the EU consent gate.
- The response has a one-line XSSI-prevention prefix (`)]}'`-style) that must be stripped before `JSON.parse`. The parsed shape is Google's typical deeply-nested undocumented array-of-arrays: `listData[0]` is the metadata block, `[4]` is the list name, `[8]` is the items array; per item, `item[2]` is the name, `item[3]` is a note, and `item[1][5]` is the coords sub-array where `[2]`/`[3]` are **lat/lng in that order** (not GeoJSON `[lng,lat]`). A Google feature ID (`google_ftid`, passed through to `ctx.collections.savePlace()` for parity with what TREK's own core import produces) is extracted via `googleMapsFeatureIdFromItem()`/`googleMapsHexId()` — ported verbatim from TREK core, checking two possible nested locations (`item[1][6]` or `item[7][1]`) and BigInt-encoding a signed decimal ID into TREK's `0x...` hex convention when needed.
- Naver's `naver.me` short links resolve the same way (follow redirect, regex out a `favorite/myPlace/folder/<id>` folder ID), but the actual data API — `https://pages.map.naver.com/save-pages/api/maps-bookmark/v3/shares/<folderId>/bookmarks?...` — is a normal, documented-shape JSON API, not an undocumented array walk: `item.py`/`item.px` are lat/lng (Naver's own y/x-order field names), `item.name`/`item.displayName`, `item.memo` (notes), `item.address`. It's genuinely paginated (`start`/`limit=20` against `folder.bookmarkCount`), looped here up to a 500-place cap per call as a sanity bound (TREK core's own version has no cap at all, looping the full `bookmarkCount`).

**This is an undocumented, unofficial technique with no stability guarantee** — same caveat TREK's own core code carries; there's no fallback if either endpoint's shape changes. A single-*place* share link (as opposed to a *list* link) is explicitly rejected with a pointed error message (`/maps/place/` in the resolved URL) rather than a confusing "no list ID found", mirroring TREK core's own UX for that same case.

**Confirmed against a real instance: naively following the redirect chain to its end breaks, because it runs straight into the consent wall this whole approach was supposed to route around.** The first implementation used a generic `fetchFollowRedirect()` that always resolved a short link all the way to its final URL, one explicit `fetch()` per hop, then ran the list-ID regexes only against that final URL. In production this returned `{"error":"egress: consent.google.com is not in the plugin's declared hosts"}` — the real `maps.app.goo.gl` chain is `maps.app.goo.gl → www.google.com/maps/@/data=...!2s<listId>... → consent.google.com/ml?...`, and the second hop, not the first, is where the chain actually lands when followed to completion. Adding `consent.google.com` to egress would be the wrong fix — TREK core's own `importGoogleList()` never needs to *read* that page either (it has no plugin-style egress restriction, so it simply doesn't care which host it lands on before extracting the substring). **The list ID is already present one hop earlier** — in the `Location` header of the *first* redirect (the `www.google.com/maps/@/data=...` URL), before the second hop is ever fetched. Fixed by replacing `fetchFollowRedirect()` with `resolveRedirectChain(url, matchFn, timeoutMs)`, which checks `matchFn` (a per-route closure running the list-ID/folder-ID regex) against each redirect's `Location` header **before** deciding whether to fetch it, and returns immediately on a match — so the never-declared, never-needed `consent.google.com` hop is never actually requested. Any future pattern-extraction-from-a-redirect-chain code in this plugin should use `resolveRedirectChain()`, not a bare "follow to the end" resolver — a short link's *final* destination is not a safe assumption when intermediate hosts (consent walls, login walls, tracking redirectors) may be neither reachable nor necessary.

New egress needed for this, since it's a materially larger footprint than the plugin's previous single-domain (`nominatim.openstreetmap.org`) + CDN (`polarsteps.s3.amazonaws.com`) egress list: `www.google.com`, `maps.app.goo.gl`, `goo.gl`, `naver.me`, `pages.map.naver.com` — both in `permissions` (as `http:outbound:*`) and `egress`. Done server-side, not client-side, deliberately: even if CORS didn't block a browser-side fetch to these endpoints (it likely would, since neither sets permissive `Access-Control-Allow-Origin` headers for arbitrary origins), Node's `fetch` has no CORS enforcement at all, making server-side the only reliable option — consistent with `reverseGeocode()`'s own precedent of hitting external APIs from `server/index.js`, not the client.

### External API usage

`reverseGeocode(lat, lng)` calls `nominatim.openstreetmap.org/reverse` directly with `fetch`, always followed by `sleep(1100)` to respect Nominatim's 1 req/sec limit. `ctx.*.create()` calls are also throttled with small sleeps (80-150ms) between iterations during bulk import. Any new external call must be added to both `permissions` (`http:outbound:...`) and `egress` in `trek-plugin.json`.

### Versioning

`trek-plugin.json`'s `"version"` and the `onLoad` log string in `server/index.js` (`'trip-importer vX.Y.Z loaded'`) are two independent literals — nothing keeps them in sync automatically. They had drifted apart before (`1.3.2` vs `v1.3.1`); update both together on every version bump.
